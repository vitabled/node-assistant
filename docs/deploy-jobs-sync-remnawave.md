# «Деплой нод» ⇄ Remnawave: синхронизация карточек и tombstones

> Краткая версия — `CLAUDE.md` §23; здесь — подробности.

Задача владельца: «в na убери ноды в деплое нод, которых нет в remnawave, и добавь недостающие».
Remnawave — источник правды по составу нод, карточки — инвентарь оператора, поэтому сверка идёт
ПО РУЧКЕ, а не таймером: при открытии страницы «Деплой нод» ничего не меняется.

## Ручка

**`POST /api/deploy-jobs/sync-remnawave`** — тело `{"dry_run": true|false}`, ответ:

```json
{
  "ok": true,
  "dry_run": false,
  "added":   [{"taskId": "rw-<uuid>", "ip": "203.0.113.5", "domain": ""}],
  "removed": [{"taskId": "dead-1",     "ip": "45.11.22.33", "domain": "dead-1.example.com"}],
  "skipped": [{"ip": "172.30.0.1", "reason": "private-address"}],
  "nodes_total": 5, "cards_before": 6, "cards_after": 4
}
```

`dry_run=true` не пишет НИЧЕГО: сначала показываем «добавить N: …» / «убрать M: …», применяем только
по подтверждению (модалка `RemnawaveSyncModal` в `DeployDashboard.tsx`). Имена полей — `added`/`removed`
(в черновике задания было `add`/`remove`; контракт оркестратора — `added`/`removed`).

- **add**: нода Remnawave, чей `address` не совпадает ни с одним `ip` карточек, получает карточку формата
  `DeployJob` с синтетическим СТАБИЛЬНЫМ `taskId` = `rw-<uuid ноды>` — повторный прогон дублей не плодит.
- **remove**: только карточки, у которых расшифрованная форма `mode == "remnanode"` И `ip` отсутствует
  среди адресов нод Remnawave.
- ⚠️ **Никогда не удалять** карточки с `mode != "remnanode"` (HAProxy-реле в Remnawave не регистрируются —
  это норма, их форма держит доступы и домен) и карточки, чей IP в Remnawave ЕСТЬ, даже если нода сейчас
  недоступна. Единственный признак «мёртвая» — отсутствие адреса в панели.
- Приватные/служебные адреса (`10/8`, `172.16/12`, `192.168/16`, `127/8`; на бою это внутренний
  docker-адрес `172.30.0.1`) карточек не получают и уходят в `skipped` с причиной `private-address`.
- **Креды новой карточки берутся ТОЛЬКО из серверного стора `node_creds.json`**
  (`app/services/node_creds.py`, read-only и толерантный к формату: битый JSON или неизвестная форма =
  «доступов нет»). Нет записи — карточка всё равно создаётся, но БЕЗ пароля: выдумывать SSH-пароли
  нельзя. `newSshPort` — из стора, иначе дефолт настроек аккаунта (`deploy_defaults.new_ssh_port`, 2222).
- В Remnawave не пишется ничего: только `list_nodes()` (GET `/api/nodes`).

## Tombstones — почему без них удаление откатывалось

Карточки кэшируются в браузере (`localStorage`, ключ `deploy_jobs_<accountId>`), а `deployJobsSync.ts`
синхронизирует АДДИТИВНО: карточка, удалённая на сервере, но оставшаяся в кэше, уезжала обратно как
`localOnly` и «воскресала». Теперь сервер помнит удалённые `taskId`
(`deploy_jobs_tombstones.json` в каталоге аккаунта):

- `GET /api/deploy-jobs` tombstone-нутые карточки не отдаёт;
- `POST /api/deploy-jobs` (upsert) для такого `taskId` отвечает `200` с `ignored: true` и карточку
  НЕ воссоздаёт;
- `GET /api/deploy-jobs/tombstones` → `{"taskIds": [...]}`. Клиент вычищает такие карточки из
  `localStorage` ДО мержа и не отправляет их наверх; ручка необязательна — старый бэкенд без неё синк
  не ломает;
- ⚠️ `_LOCK` в `deploy_jobs.py` — `RLock`: helpers томбстонов зовутся изнутри уже залоченных
  `upsert`/`delete`;
- если нода снова появилась в Remnawave, синхронизация снимает tombstone — карточка нужна заново.

## Карточка без кредов

Рисуется как «существующий сервер» без живых данных: жёлтый кружок «нет SSH-пароля» вместо зелёной
галочки (`lacksSshCreds` в `DeployCard.tsx`), стрим задачи отвечает «Task not found» и закрывается без
реконнектов (коммит `421bd03`), а неудачный сбор статистики по SSH проглатывается без ошибки на экране.
