## Порядок реализации

```
A (Ф1 стор+API → Ф2 ядро key-auth) ──► C (Ф1 каркас+RuVDS ──► Ф2-Ф5 адаптеры ──► Ф6 фоновый луп)
   │                                        ▲
   └── Ф3-Ф6 раскатка key-auth + фронт      │ креды провайдеров живут в волте A
                                            │
B (Ф0 разведка ──► Ф1 подключение ──► Ф2 биллинг ──► Ф3 домены) ──► C Ф7 (CF как провайдер)
```

- **A Ф1 первым и обязательно** — от волта зависят и автоподстановка кредов, и План C.
- **B независим от A** (токен CF лежит в `AppSettings.cloudflare.api_token_enc` по конвенции «один секрет на
  модуль»), поэтому может идти параллельно; его Ф0-разведка на живом аккаунте — самая дешёвая работа во всей
  волне, полезно сделать сразу.
- **C после A Ф1**, а не после всего A: адаптерам нужен только `vault_store.read_fields`, не key-auth.
- **Oracle (C Ф5) и раскатка key-auth на 13 остаточных call-site'ов (A Ф5) — последние**: самые скучные и
  самые рискованные соответственно.

## Сквозные решения (действуют во всех трёх планах)

1. **Правило размещения секретов** (новое, в CLAUDE.md): один секрет на модуль → `AppSettings.<module>.<name>_enc`
   (Fernet, наружу только `has_token`); много однотипных пользовательских секретов → **Хранилище** (`vault.json`,
   поле `fields_enc`). Именно поэтому CF-токен — в настройках, а креды 8 провайдеров — в волте.
2. **Расширение module-scoped override «секреты at-rest».** До Волны 9 на сервере лежали только секреты
   инфраструктуры (MCP/HAProxy/AI/rules/infra-billing). Теперь там могут лежать **SSH-пароли и приватные ключи
   пользователя** — по его явной просьбе. Следствия, которые надо проговорить в README и в UI:
   `ENCRYPTION_KEY` из `.env` становится ключом ко всему Хранилищу; его потеря = потеря записей, дефолтный
   dev-ключ = любой может расшифровать. Резервная копия `.env` обязательна.
3. **Секрет никогда не попадает:** в URL/query (reveal — `POST`), в логи задач, в текст ошибок внешних API
   (`_redact` в каждом клиенте), в `localStorage` (приватные ключи ездят как `ssh_key_ref`).
4. **Внешние API:** фиксированный хост → без SSRF-гарда (CF, RuVDS, Yandex, Beget, Veesp, Reg.ru);
   пользовательский base_url → `net_guard.is_safe_url` **и при сохранении, и на каждом запросе**
   (OpenStack/VK/Procloud) — как в `nodeflow_client`.
5. **Новых pip-зависимостей нет.** `cryptography` (есть) закрывает PS256-JWT Yandex и RSA-подпись Oracle;
   `httpx` (есть) — все клиенты. SDK провайдеров (`oci`, `openstacksdk`) сознательно не тянем ради 2-3 запросов.
6. **Деньги.** Единственная операция, тратящая деньги — покупка домена (B Ф3). Гейты: `confirm:true`,
   **совпадение `expected_price` с только что снятой ценой**, наличие способа оплаты у CF, `auto_renew=false`
   по умолчанию, двойное подтверждение в UI. Платёжные реквизиты панель не собирает и не вводит — CF списывает
   со своего сохранённого способа оплаты.
7. **Проверено / не проверено** — помечать честно. Живьём проверяемо: CF read-ручки (Ф0-скрипт), RuVDS (есть
   спека + токен), деплой по SSH-ключу. Не проверяемо без кредов/денег: покупка домена, часть адаптеров
   (Oracle/VK/Procloud/Veesp/Beget) — в CLAUDE.md напротив каждого написать «только по документации».
