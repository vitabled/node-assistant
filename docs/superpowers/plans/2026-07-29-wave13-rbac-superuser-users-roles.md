# Волна 13 — суперпользователь, пользователи и роли вместо мультиаккаунтинга

> Запрос (2026-07-29): «Нужно переделать систему мультиаккаутинга. При первом запуске сервиса появляется
> окно создание суперпользователя. Систему регистраций убери. В настройки добавь вкладку "Роли",
> "Пользователи". "Пользователи": Тут можно создать пользователя, добавить/убрать роль пользователю,
> изменить пароль пользователя. "Роли": Тут можно создавать/изменять параметры ролей пользователей.
> Роль — набор привилегий. Пользователи с ролью приобретают привилегии роли. Привилегии продумай сам,

Это **план**, не реализация. Он опирается на прочитанный код, а не на память: все ссылки вида `файл:строка`
сверены. Разделы «Развилка», «Последствия» и «Нужно решение» — то, что надо подтвердить ДО кода.

## 1. Развилка, которую надо закрыть первой: «аккаунт» — это тенант или человек?

Сегодня аккаунт — **тенант**: у каждого свои `settings.json`, `hostings.json`, `infra_billing.db`, своя история
мониторинга. Два аккаунта не видят данных друг друга вообще.

Суперпользователь + роли подразумевают обратное: **одна установка, одни данные, разные люди с разными правами**.
Это не надстройка над текущей моделью, а другая модель.

### Предлагаемое решение: расщепить «аккаунт» на РАБОЧУЮ ОБЛАСТЬ и ЛИЧНОСТЬ

- `current_account` **остаётся** — но означает теперь **рабочую область** (scope данных). По умолчанию она одна
  на установку.
- Появляется `current_user` — личность: логин, роли, привилегии, версия токена.

**Почему именно так, а не переписать сторы:** `current_account` читают ~15 модулей (`storage.py`,
`infra_billing_store`, `hostings_store`, `vault_store`, `library_store`, `media_store`, `server_monitor_store`,
`speedtest_store`, `user_stats_store`, `subpage_store`, `rules_store`, `sync_store`, `testserver_registry`,
`checker_registry`, `config_templates_store`), причём часть — из фоновых лупов, где запроса нет вовсе. Сохранив
смысл «где лежат данные» за прежним ContextVar, мы получаем RBAC, **не тронув ни один стор и ни один фоновый
луп**. Это разница между волной и полугодовым рефакторингом.

### Что делать с уже существующими аккаунтами (миграция без потерь)

При старте новой версии реестр может содержать N аккаунтов, у каждого — свои данные на диске.

1. Аккаунт с минимальным `created_at` → его каталог становится **рабочей областью установки**, а его логин —
   **суперпользователем** (пароль сохраняется, повторный ввод не нужен).
2. Остальные аккаунты → превращаются в **пользователей** этой рабочей области с ролью, которую выберет
   суперпользователь (по умолчанию — «Наблюдатель»).
3. ⚠️ **Их данные НЕ сливаются автоматически.** Каталоги `accounts/<id>/` остаются на диске нетронутыми, а
   суперпользователь видит их в разделе «Пользователи» как «архив данных прежнего аккаунта» со ссылкой на
   экспорт (`/api/export` умеет собрать архив по конкретной области). Автоматический мерж невозможен без
   правил разрешения конфликтов для 15 разных сторов — придумывать их за пользователя нельзя, а тихо потерять
   его данные нельзя тем более.
4. В записи пользователя остаётся поле `workspace_id`. Один воркспейс — обычный случай; поле нужно, чтобы
   будущий мультиворкспейс не потребовал второй такой же миграции.

**✅ Решено (2026-07-30):** прежние аккаунты 2..N **превращаются в пользователей одной области** (роль
«Наблюдатель», пароли сохраняются — люди входят прежними кредами). Их каталоги данных остаются на диске как
архив; автоматического слияния нет.

## 2. Первый запуск: окно создания суперпользователя

### Backend
- `GET /api/auth/state` — **ungated**, отдаёт `{"bootstrap": true|false, "login_hint": null}`. `bootstrap`
  истинно ⟺ в реестре нет ни одного пользователя. Ничего больше не сообщает: наличие/отсутствие пользователей —
  единственный факт, который и так виден по поведению экрана входа.
- `POST /api/auth/bootstrap` — **ungated, одноразовый**. Создаёт первого пользователя с `is_superuser=true`.
  ⚠️ Проверку «реестр пуст» делать **внутри того же `_lock`**, что и запись (`accounts.py:132`), иначе два
  одновременных запроса создадут двух суперпользователей. После успеха ручка обязана отвечать `409` навсегда.
- `POST /api/auth/register` — **удалить целиком** вместе с тестами, которые её вызывают (их много: почти каждый
  тест бэкенда регистрируется через неё, см. `_register()` в `tests/test_ai_prompts.py:20` и десятках других).
  ⚠️ Это самая объёмная механическая часть волны: нужен общий тестовый хелпер `tests/conftest.py::make_user()`,
  который создаёт пользователя напрямую через сервис, а не по HTTP. Иначе правка расползётся по ~40 файлам.

### ⚠️ Гонка первого запуска — назвать риск прямо
Публичная ручка `bootstrap` означает: кто первым дошёл до свежей установки, тот и суперпользователь. Для
панели, которую поднимают одной командой (`install.sh`) и сразу открывают, это обычный компромисс first-run
визарда. Смягчение — **опционально** и по выбору:

**✅ Решено (2026-07-30, на моё усмотрение): `BOOTSTRAP_TOKEN` — опциональный.**
- Пустой (по умолчанию) → `bootstrap` работает как обычный first-run визард. Ровно то поведение, которого ждёт
  человек, поднявший панель одной командой.
- Непустой → `bootstrap` требует его в теле, иначе `403`.
- Ровно тот же приём, что у `AGG_TOKEN` (§4b Ф8): «пусто = выключено» уже принятая в проекте форма
  опционального заголовка-секрета, и вторую конвенцию заводить незачем.
- `install.sh` его НЕ генерирует сам: молча включённый гейт превратит первый вход в «403 без объяснений».
  Вместо этого в `README.md` рядом с командой установки — абзац «сразу зайдите и создайте суперпользователя, а
  если установка стоит в открытом интернете и вы вернётесь к ней позже — задайте `BOOTSTRAP_TOKEN` в `.env`».

### Frontend
- `AuthScreen.tsx` (235 строк) — режим `register` удалить, добавить режим `bootstrap`: два поля + подтверждение
  пароля + «Сгенерировать пароль» (генератор уже есть — `store.ts:118`), с той же янтарной плашкой «пароль
  нигде не сохраняется». Выбор режима — по `GET /api/auth/state` на маунте.
- Пока `state` не загрузился — не показывать ни одну из форм: мигание «Регистрация → Вход» на первом запуске
  выглядит как сбой.

## 3. Модель привилегий

### Форма привилегии
`<домен>.<действие>`, где действие — одно из **четырёх**, как и просил запрос:

| Действие | Смысл | Методы |
|---|---|---|
| `view` | смотреть | `GET` |
| `create` | добавлять новое | `POST` на коллекцию |
| `edit` | менять и удалять существующее | `PUT`, `PATCH`, `DELETE` |
| `execute` | запускать операции: деплой, SSH-шаг, синк, замер, покупка | `POST`-действия |

⚠️ **Почему удаление внутри `edit`, а не пятым действием:** запрос называет ровно четыре, а разнести
«изменить» и «удалить» по разным привилегиям во всех 16 доменах — это 16 лишних галочек в UI, которые почти
всегда будут стоять вместе. Там, где удаление действительно необратимо и дорого, оно и так проходит по
`execute` (снос панели, восстановление из бэкапа) либо закрыто отдельной привилегией из таблицы ниже.

### Домены (16) — по разделам навигации, а не по файлам
`dashboard`, `deploy`, `panel`, `certs`, `hosts`, `configs`, `automation`, `assistant`, `monitoring`, `stats`,
`hostings`, `billing`, `cloudflare`, `haproxy`, `library`, `vault`, `settings`, `admin`.

(Восемнадцать вместе с `settings`/`admin`; в UI ролей — 18 строк по 4 галочки, это ещё читаемо, а 30 уже нет.)

### Особые привилегии, которые НЕ выводятся из CRUD
Их вводить отдельно, потому что они меняют не данные, а саму установку или её деньги:

| Привилегия | Что открывает |
|---|---|
| `admin.users` | «Пользователи»: создание, роли, смена пароля |
| `admin.roles` | «Роли»: создание и правка наборов привилегий |
| `admin.infrastructure` | обновление панели (`/api/updates/apply`), развёртывание NodeFlow/Certwarden/Netbird, старт-стоп общих контейнеров (MCP, CLIProxyAPI, xray-checker) |
| `admin.export` | выгрузка и загрузка данных аккаунта (`/api/export`, `/api/import`) — один вызов уносит всё |
| `vault.reveal` | посмотреть значение секрета. **Отдельно от `vault.view`**: видеть список записей и видеть пароли — разные права |
| `billing.purchase` | покупка ресурсов у провайдера и домена в Cloudflare — тратит деньги |
| `deploy.credentials` | передавать SSH-креды в запросе (деплой, `node/step`, замеры). Без неё пользователь видит ноды, но не может ходить по ним |

### Готовые роли (создаются при миграции, редактируемые)
- **Суперпользователь** — не роль, а флаг `is_superuser`: обходит таблицу целиком. Нужен как аварийный выход,
  когда роли настроили неудачно.
- **Администратор** — всё, кроме `admin.users`/`admin.roles`.
- **Оператор** — `view` везде + `deploy.*`, `certs.*`, `monitoring.*`, `automation.edit`, `deploy.credentials`.
  Без `vault.reveal`, `billing.purchase`, `admin.*`.
- **Финансы** — `billing.*` (кроме `purchase`), `hostings.*`, `view` на остальном.
- **Наблюдатель** — только `view`, и без `vault.view`.

## 4. Как это применить, не правя 220 маршрутов

### Декларативная таблица «маршрут → привилегия» + запрет по умолчанию
Новый модуль `backend/app/services/permissions.py`:

```python
# (шаблон маршрута, метод|"*") → привилегия
RULES: tuple[tuple[str, str, str], ...] = (
    ("/api/hostings",              "GET",   "hostings.view"),
    ("/api/hostings",              "POST",  "hostings.create"),
    ("/api/hostings/{hosting_id}", "*",     "hostings.edit"),
    ("/api/vault/{entry_id}/reveal", "*",   "vault.reveal"),
    ...
)
```

⚠️ **Сопоставлять по `request.scope["route"].path` — по ШАБЛОНУ маршрута, а не по сырому URL.** Starlette к
моменту вызова зависимости уже отмаршрутизировал запрос, поэтому шаблон канонический по построению: ни
`%2e%2e`, ни `//`, ни `.` в нём быть не может. Это ровно та ошибка, на которой в Волне «ассистент» сломался
денилист моста (`ai_tools/bridge.py`, CLAUDE.md §20h): там путь приходил строкой и его приходилось
канонизировать вручную. Здесь этой работы нет — и не надо её изобретать.

**Запрет по умолчанию:** маршрут, которого нет в таблице, доступен **только суперпользователю**. Новый роутер,
добавленный и не размеченный, не становится общедоступным — он просто не работает у обычного пользователя, и
это заметно сразу.

**Тест покрытия (обязательный):** проходит по `app.routes`, и для каждого `/api/*` требует запись в `RULES`.
Падает при добавлении роутера без разметки. Это единственный способ не дать таблице отстать от кода —
тот же приём, что `endpoints()` в мосте ассистента, читающий реальную таблицу маршрутов.

### Точка применения
Переименовать `require_account` → **`require_identity`** (старое имя оставить псевдонимом на одну волну, чтобы
не переписывать `main.py` и тесты одним куском) и добавить внутрь:

1. разбор кредов (как сейчас) → `user_id`;
2. загрузка пользователя: выключен → `403`; версия токена не совпадает → `401`;
3. `current_user.set(user)`, `current_account.set(user.workspace_id)`;
4. `permissions.check(request, user)` → `403` с внятным текстом «нужна привилегия `hostings.create`».

### Как это ложится на API-токены
- Формат меняется на `nai_<user_id>_<secret>` (внутри — id пользователя, а не воркспейса).
- Привилегии токена **не хранятся** — берутся у пользователя в момент запроса. Тогда снятая роль немедленно
  обесточивает и его токены, без обхода по хранилищу.
- Флаг `readonly` остаётся как есть: он **сужает** права до `GET`, а не расширяет.
- ⚠️ Существующие токены содержат id воркспейса и станут неопознаваемыми. Правильно — **инвалидировать их при
  миграции** и сказать об этом в UI: молча оставить работающим токен, чьи права теперь считаются по другому
  субъекту, хуже, чем заставить перевыпустить.

### Как это ложится на встроенного ассистента (важно, только что построено)
`ai_tools/bridge.py:call()` минтит токен через `accounts.issue_token(account_id)` и ходит в наш же REST. Под
RBAC это **потенциальная эскалация**: ассистент получил бы права воркспейса, а не своего хозяина.

Лечение простое ровно потому, что права не лежат в токене: минтить токен **того же пользователя**
(`issue_token(user_id)`). Тогда ассистент по построению не может больше своего хозяина, а денилист моста
остаётся вторым слоем (деньги, секреты, инфраструктура) — он запрещает и то, что пользователю разрешено.
То же касается `mcp_server.start`, который минтит управляемый readonly-токен: привязать к пользователю,
включившему MCP.

### Что НЕ покрывается привилегиями (сказать вслух)
- Фоновые лупы (`poller_loop`, `rules_loop`, `monitor_loop`, `provider_sync`, `auto_backup`, `updater`) работают
  от имени воркспейса, запроса и пользователя у них нет. Правило, заведённое пользователем с `automation.edit`,
  выполнится фоном вне всяких проверок — та же природа, что и находка «отложенное выполнение» из §20h.
  Следствие: **`automation.edit` надо считать привилегией уровня оператора, а не наблюдателя.**
- `/ws/logs/{task_id}` остаётся капабилити (браузер не может поставить заголовок на рукопожатии WS). Задачу
  можно смотреть, зная неугадываемый id. Оставляем, но пишем в план явно.
- Общие DooD-контейнеры (MCP, CLIProxyAPI, NodeFlow, xray-checker) — одни на установку. `admin.infrastructure`
  ограничивает, кто может их запускать, но не делает их персональными.

## 5. Последствия, которые нельзя проглядеть

### ⚠️ Карточки деплоя живут в браузере — коллега их не увидит
`deploy_jobs_<id>`, `panel_jobs_<id>`, `cert_jobs_<id>` лежат в localStorage **потому что несут SSH-креды**, а
проект их на сервере не хранит (кроме осознанного исключения — Хранилища, §15a). Ключи привязаны к id
аккаунта. После расщепления они станут **пер-пользовательскими**: оператор не увидит нод, которые задеплоил
администратор.

Это регрессия в глазах пользователя, и её надо решить осознанно, а не обнаружить:
- **Вариант A (рекомендую):** оставить как есть, а общей картиной сделать серверные данные — «Доступность
  серверов» (`server_monitor`, уже серверный) и ноды Remnawave. В карточке деплоя ценно ровно то, что она
  помнит креды; делиться ими между людьми не нужно.
- **Вариант B:** хранить карточки на сервере **без кредов** (ip, домен, статус, шаги), а креды оставить в
  браузере. Тогда список общий, а «переустановить компонент» просит креды заново.
- **Вариант C:** класть креды в Хранилище и ссылаться на запись (`ssh_key_ref` уже так работает, §15c).
  Самый удобный и самый спорный: превращает браузерный секрет в серверный.

**✅ Решено (2026-07-30): вариант A.** Карточки остаются пер-пользовательскими, общей картиной служат серверные
данные — «Доступность серверов» (`server_monitor`) и ноды Remnawave. Кода это не требует вовсе; требует записи
в CLAUDE.md и строки в UI, иначе «коллега не видит мою ноду» будут считать багом.

### Прочие пер-аккаунтные ключи браузера
`ni_tab_<id>`, `ni_skin_<id>`, `ni_thememode_<id>`, `xray_profile_<id>`, раскладка виджетов статистики — все
станут пер-пользовательскими. Здесь это **правильно** (тема и открытая вкладка — личное дело) и менять нечего.
Серверное зеркало внешнего вида (`AppearanceConfig`, §2a) переедет на пользователя.

### Смена пароля должна отзывать сессии
Сегодня JWT не содержит ни `exp`, ни версии, поэтому уволенный сотрудник со сохранённым токеном продолжит
работать после смены пароля. Ввести `token_version` в записи пользователя и клейм `ver` в JWT; бампить при
смене пароля, изменении ролей, выключении и удалении. `exp` по-прежнему не добавлять — «постоянная сессия, как
у Google» была осознанным решением, а отзыв решается версией.

### Защита от самоблокировки и самоповышения
- Нельзя снять `is_superuser` с **последнего** суперпользователя, удалить его или выключить.
- **Правило неусиления:** выдать роль можно только если выдающий сам обладает **каждой** привилегией этой роли.
  Иначе пользователь с `admin.users` соберёт себе роль с `admin.infrastructure` и получит всю установку.
  Суперпользователь от правила освобождён.
- Правку `admin.roles` у роли, которая на тебе висит, не запрещаем — но предупреждаем в UI: можно отрезать себе
  доступ к разделу «Роли».

### Пароли
`Credentials.password` сейчас `min_length=1` (`api/auth.py:21`). Для многопользовательской установки ввести
минимум 10 символов — но **только на установку и смену**: поднять требование к уже существующим хешам
невозможно, а выкидывать людей из панели за старый пароль нельзя.

### Журнал действий
Завести `DATA_DIR/audit.log` (JSONL, append-only): `{ts, user_id, login, method, route, allowed, status}` для
всех НЕ-`GET` запросов и всех отказов по привилегии. В многопользовательской панели «кто отключил ноду» — первый
вопрос, который задаст владелец. Ротация по размеру, без внешних зависимостей.

## 5a. Сброс входа суперпользователя из установщика

Забытый пароль единственного суперпользователя = запертая установка: восстановления по почте в панели нет и
быть не должно (SMTP мы не держим). Значит выход обязан быть у того, у кого есть shell на хосте.

### `node-assistant reset-admin`
Новая команда в `install.sh` (диспетчер уже есть — §14c: `install`/`status`/`check-updates`/`update`/
`set-domain`/`set-ports`).

```
node-assistant reset-admin [--login <логин>] [--password <пароль>] [--generate]
```

- Без флагов — спрашивает логин и пароль через `/dev/tty` (не stdin: скрипт умеют запускать через `curl | bash`,
  и `read` съел бы остаток скрипта — §14c).
- `--generate` — генерирует пароль, печатает **один раз** в вывод и предупреждает, что он нигде не сохранён.
- Если суперпользователей несколько, `--login` обязателен: угадывать, чей пароль сбрасывать, нельзя.
- Указанного логина нет → ошибка со списком существующих суперпользователей (это уже привилегированный
  контекст, скрывать логины не от кого).

### Как это технически исполняется
Данные лежат в docker-томе `node-installer_node-data`, у хоста прямого доступа к ним нет. Поэтому команда
работает через одноразовый контейнер того же образа:

```
docker compose run --rm --no-deps -T backend python -m app.reset_admin --login … --password-stdin
```

- ⚠️ **Пароль передаётся через stdin, а не argv.** В argv он попал бы в `/proc/cmdline` и в историю оболочки —
  то же правило, по которому секреты панели уходят на ноду через `SSHSession.get_script_output` (§6).
- `--no-deps`, потому что для правки `users.json` не нужен ни один зависимый сервис.
- `-T` обязателен: без него `compose run` требует TTY и падает в неинтерактивном контексте.
- Работает и при остановленном стеке (`run`, а не `exec`) — пароль забывают именно тогда, когда всё лежит.

### `backend/app/reset_admin.py` (новый CLI-модуль)
- Читает пароль из stdin, вызывает `users.set_password(...)` + **бампит `token_version`** (иначе прежние сессии
  переживут сброс — а сбрасывают пароль как раз тогда, когда доступ надо отобрать).
- Если суперпользователя нет вовсе (реестр пуст) — не создаёт его молча, а печатает «реестр пуст, откройте
  панель и пройдите первичную настройку»: тихое создание владельца из командной строки — это второй путь
  bootstrap, и его пришлось бы защищать отдельно.
- Флаг `--reopen-bootstrap` **намеренно НЕ делаем.** Снести суперпользователя, чтобы визард открылся заново, —
  значит открыть окно, в котором владельцем станет любой, кто первым зайдёт. Сброс пароля решает ту же задачу
  без этого окна.
- ⚠️ Это **не** ослабление модели: у кого есть shell на хосте, тот уже читает и `ENCRYPTION_KEY`, и все
  Fernet-волты, то есть может подделать JWT любого пользователя. Команда лишь делает законный путь удобнее
  незаконного. Записать это в докстринг, чтобы через полгода её не «закрыли ради безопасности».
- Пишет в журнал действий (§5) запись с `user_id=null` и пометкой `source="cli"`.

## 6. Frontend

### Раздача привилегий на клиент
`GET /api/auth/me` → `{id, login, is_superuser, roles: [{id, name}], permissions: ["hostings.view", …]}`.
Хук `usePermissions()` + `can("hostings.create")`.

⚠️ **Скрытие пунктов в UI — косметика, а не защита.** Единственная граница — сервер. Прописать это в докстринге
хука, чтобы через полгода никто не «сэкономил» на серверной проверке, увидев, что кнопки и так не видно.

- `Sidebar.tsx` — прятать пункты и целые группы без `<домен>.view`. Пустая группа не рисуется.
- `App.tsx` — если восстановленная из `ni_tab_<id>` вкладка недоступна, откатываться на `dashboard`, а не
  показывать пустой экран.
- `AccountMenu` — «Добавить аккаунт» → «Войти другим пользователем» (тот же экран входа, регистрации нет).
  Устройство по-прежнему помнит несколько сессий: админ и оператор за одним ноутбуком — реальный случай.

### Новые вкладки настроек
`SubTab` (`Settings.tsx:786`) += `"users" | "roles"`, обе видны только при `admin.users` / `admin.roles`.
Многорядный `.seg-wrap` уже поддержан (§11f) — 15 вкладок разложатся.

**`settings/UsersTab.tsx`**
- Список: логин, роли чипами, «выключен», последний вход.
- Создание: логин + пароль (с генератором) + роли. Пароль показывается **один раз** — тот же приём, что у API-токенов (§1b), с янтарной плашкой.
- Правка ролей — мультиселект (`MultiSelect` уже приведён к токенам темы).
- «Сменить пароль» — вводит **новый** пароль пользователя. Своего старого пароля суперпользователь не знает и
  знать не должен; предупредить, что смена завершит все сессии этого пользователя.
- «Выключить» вместо удаления по умолчанию: удаление пользователя, чьи действия есть в журнале, оставляет
  висячие ссылки. Удаление — второй, подтверждаемый шаг.

**`settings/RolesTab.tsx`**
- Список ролей + число носителей (удаление роли, которая на кого-то надета, требует подтверждения и снимает её).
- Редактор — **матрица 18 доменов × 4 действия** галочками + отдельный блок «Особые привилегии» из §3.
  Кнопки-шаблоны «Оператор», «Наблюдатель» заполняют матрицу целиком: собирать 72 галочки руками ради типовой
  роли — не работа для человека.
- Встроенные роли помечены и правятся, но не удаляются (иначе установка останется без «Наблюдателя»).
- Показывать `403`-причину из бэкенда дословно: «нужна привилегия X» полезнее, чем «недостаточно прав».

## 9. Чего этот план НЕ делает

- Не вводит мультиворкспейс с переключателем (поле `workspace_id` заложено, UI — нет).
- Не сливает данные прежних аккаунтов (см. §1, пункт 3).
- Не делает привилегии для фоновых лупов — им не от кого их получать (§4).
- Не трогает 15 сторов и ContextVar `current_account`: в этом и весь смысл расщепления.
- Не добавляет `exp` в сессионный JWT — отзыв решается `token_version`.
- Не вводит SSO/LDAP/2FA. Если это нужно, это отдельная волна: 2FA поверх bcrypt+JWT ложится, но требует
  экрана восстановления, иначе первый же потерянный телефон запирает установку.
